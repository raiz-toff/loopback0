# Landing pages: the first screen is the pitch

Links shared on social sites open on the shared URL, usually in a phone's in-app browser. The home page (`/`) is not shared, so it is not a landing page.

- Landing pages: the project list (`/docs/projects`), the blog list (`/blog`), each project's overview page (`/docs/projects/<name>`), and every blog post.
- On these pages the first screen must carry, in order: what it is in one line, a visual of the real thing (screenshot, recording, live embed), then the actions.
- On a blog post, the first section decides whether the reader stays. Open with the result or the problem, not background.
- Check every change to these pages at phone width.
- Mock up changes to these pages in the unlinked `/demo-lab` route first. Apply them to the real pages only after the user approves.

# Page intro: the description is the only one

The page layout prints the frontmatter `description` under the title, on every docs page and blog post. The same field also feeds meta tags, share cards, RSS, search and the project cards.

- The description is the page's only intro. Never open the body with a paragraph that restates it.
- If the body's opening has a fact the description lacks, move that fact into the description. Then delete the repeat.
- Start the body with something new: the first step, the result, the problem, or the visual.
- Never put an H1 in the body. The layout already prints the title.
- Never leave a description empty or vague ("A guide to fix X problem"). Write it to the standard of the page type:
  - Lab guide: one imperative line. Example: "Configure VLANs on a Cisco 2960 switch and assign access ports to them."
  - Blog post: the result or the problem.
  - Project: what it is and who it is for.
- Lab guides: a "Lab objectives" section only lists steps the description does not cover, as a bullet list. If it would only repeat the description, leave it out.
- Overview components: `OverviewHero`'s `lead` holds only facts the description does not state. Omit `lead` rather than repeat the description.

# Overview pages: the front door of every section

The main page of a section or project (the page that lists what is inside it) is its front door. Examples: `/docs/projects`, `/docs/labs`, `/docs/ccna-labs`, and a project's own `index.mdx`.

- Always label it **Overview** in the sidebar. Never repeat the section name there (not "Projects" inside Projects).
  - This applies at every level: inside a project or lab folder too. Under MileWage the first item is "Overview", not a second "MileWage".
  - Exception: a folder with only one page keeps its own name (Marrow, tunit). There is no second page for "Overview" to sit beside.
  - Section root (`root: true`): in the folder's `meta.json`, list `"[Overview](/docs/<section>)"` and `"!index"` in place of `"index"`.
  - Folder inside a section: in its `meta.json`, list `"[Overview](/docs/<section>/<folder>)"` in place of `"index"`.
  - The page title (`title:` in frontmatter) stays descriptive. Only the sidebar label is "Overview".
- Always design it. An overview page is never ordinary Markdown or MDX prose: no paragraphs, bullet lists or tables as the body.
  - Build the body as a React component and place it in the `.mdx` file as a single tag. Pattern: `<ProjectGrid />` in `content/docs/projects/index.mdx`, built in `src/components/docs/project-grid.tsx` and registered in `src/components/docs/mdx.tsx`.
  - Keep the `.mdx` file to frontmatter plus that tag. Do not put inline `<style>` blocks or hand-written HTML cards in it.
  - Each item gets a picture, what it does for the reader in one line, and one supporting sentence.
- When the section or project has more than one page, add a **Long story short** block with `<OverviewStory steps={…} />` from `src/components/docs/overview-parts.tsx`.
  - It applies to a project or lab series whose pages tell one story (MileWage, Comma, VLAN labs, Windows labs). It does not apply to section roots that list unrelated items (`/docs/projects`, `/docs/labs`, `/docs/ccna-labs`). It also does not apply to a CCNA domain until it has more than one finished lab.
  - Place it after the hero (picture, actions, note) and before the detail sections.
  - Write 3 to 5 steps that tell the whole story in order: the problem, what was built, what broke, where it stands now. For a lab series: what each lab achieves, in order.
  - Keep each step to one or two short sentences. Use only facts the sub-pages state.
  - Link each step to the sub-page that tells that part in full (`href`), with that page's short name (`page`).
  - It is one numbered list in a card. Not a paragraph, not a table.
- A new section or project is not finished until its overview page exists and meets these rules.
- It is a landing page, so the rules in the section above apply.

# Documentation Standards

Whenever you write or edit documentation, follow these rules strictly:

## Step 1: Request Classification (Diátaxis Framework)

Analyze the request and categorize it into one of four document types. You must strictly apply the corresponding industry standard to your output based on this classification.

**Category A: Lab Guides & Operational Procedures (How-To Guides)**
*Target:* CCNA labs, infrastructure deployments, step-by-step configurations.
*Standard:* ASD-STE100 (Simplified Technical English) + Cisco Technical Content Style Guide.
*Rules:*

- Limit instructional sentences to a maximum of 20 words.
- Use strict active voice and imperative mood (e.g., "Configure the interface", not "The interface should be configured").
- Format UI elements and dashboard clicks in bold (e.g., **Network > Routing**).
- Use single backticks for inline IP addresses, variables, and interface names (e.g., `192.168.1.1`, `GigabitEthernet0/0`).
- Use fenced monospaced code blocks (```) for all multi-line CLI outputs and configurations.

**Category B: Technical Blogs & Articles (Tutorials / Explanation)**
*Target:* Public-facing posts, framework tutorials, concept overviews.
*Standard:* Google Developer Documentation Style Guide + CommonMark.
*Rules:*

- Use sentence case for all Markdown headings (e.g., `## Configure the routing protocol`).
- Prioritize actionable information first; place theoretical background below execution steps.
- Keep paragraphs under 4 sentences.
- Use bullet points for prerequisites and feature lists.
- Use blockquotes (`> **Note:**`) for critical warnings or caveats.

**Category C: Project Documentation & Architecture (Explanation)**
*Target:* Internal repository logs, DevOps infrastructure choices, system design logs.
*Standard:* Architecture Decision Records (ADR).
*Rules:*

- Format the document using the Nygard ADR template with exact `##` headings:
  - Title: [Short noun phrase]
  - Status: [Proposed / Accepted / Deprecated]
  - Context: [Technical constraints and forces at play]
  - Decision: [The specific technical action taken]
  - Consequences: [Positive and negative downstream impacts]

**Category D: Code & API Documentation (Reference)**
*Target:* Software repositories, API integrations, component libraries.
*Standard:* JSDoc / TSDoc (for TypeScript/JavaScript) or OpenAPI.
*Rules:*

- Document all parameters, types, outputs, and side effects.
- Generate strict programmatic Docstrings detailing `@param`, `@returns`, and `@throws`.
- Exclude conversational explanations; rely strictly on type definitions and concise functional descriptions.

**Category E: Personal Memoir & Builder's Narrative (Storytelling)**
*Target:* Autobiographies, personal life stories, project retrospectives, and developer portfolios.
*Standard:* Literary Memoir & "Anti-Slop" Personal Narrative.
*Rules:*

- The "Friction First" Rule: Anchor the narrative in the struggle, not just the success. Detail the specific bugs, failed iterations, or real-world obstacles encountered. Avoid skipping straight to the victory.
- Ban "LinkedIn Speak": Strictly prohibit corporate or self-congratulatory buzzwords. Never use terms like humbled, honored, thrilled, journey, impactful, revolutionized, or navigating.
- The "Telling Detail" Technique: Replace broad summaries of time periods with hyper-specific physical or technical details. Instead of "I spent months studying," describe the specific setup of the lab, the exact error codes, or the physical environment of the workspace.
- Self-Awareness and Flaws: Present the subject (the author) objectively. Acknowledge mistakes, dead-ends, and bad code or poor decisions without attempting to immediately justify them.
- Show the "How" alongside the "What": When discussing creations, do not just list the features. Explain the mechanics of the decision-making process. Why was one framework chosen over another? What was the exact moment the logic finally clicked?
- No Forced Epiphanies: Do not wrap up sections with forced moral lessons or philosophical takeaways (e.g., "And that's when I learned that persistence always pays off"). End on the resolution of the specific problem or a factual observation.

## Step 2: Blog & Article Structure (Scannable Architecture)

All blog posts and long-form articles must follow these three structural principles so readers can scan and extract value immediately:

**1. The Scannable Skeleton**
Headings act as a table of contents. If a user reads only your headings, they should still understand your main argument.
- **The "Elevator Test":** Ensure `H2` and `H3` subheadings tell a complete, logical story on their own.
- **Descriptive labeling:** Avoid vague labels like "Getting Started" or "Next Steps." Instead, use specific, factual statements or questions (e.g., "Why This Saves You Time").
- **Strict hierarchy:** Use a single `H1` for the title, `H2`s for main sections, and `H3`s to break down complex sub-points. This serves both human reader navigation and search engine indexing.

**2. Text Density and Formatting**
Large blocks of text signal effort to the reader, leading to immediate exits. Content must be broken down visually.
- **Micro-paragraphs:** Limit paragraphs to 2 to 4 sentences. This maximizes whitespace, which improves both reading speed and comprehension.
- **Strategic bolding:** Bold the most critical takeaways, data points, or counterintuitive insights to create visual anchor points. Do not bold entire sentences or every other paragraph, as this creates visual chaos.
- **Frequent lists:** Use bulleted lists for unordered points and numbered lists for sequential steps. Lists distill complex information into a scannable format and make specific promises to the reader.

**3. Structural Delivery**
Deliver the value immediately, rather than building up to a delayed conclusion.
- **Match intent immediately:** Address exactly what the reader clicked to find within the introduction.
- **Visual interruptions:** Use images, data visualizations, blockquotes, or pull quotes to break up long sections. For technical or dense subjects, placing visual elements forces the reader to scroll, which maintains momentum and engagement.
- **Internal linking:** Embed links to other relevant content on the site. This acts as a highlighter for topics being discussed and keeps users engaged with the domain without disrupting the flow of the primary article.

## Step 3: Execution Constraints

- **Isolation:** Do not mix standards. A lab guide must not contain conversational blog prose, and a blog must not contain rigid 20-word sentence caps.
- **No Meta-Commentary:** Do not announce which standard or category you have selected. Immediately output the requested document using the correct formatting.
- **Tone:** Maintain a purely objective, professional engineering tone across all outputs. Remove filler words, assumptions, and subjective adjectives.
